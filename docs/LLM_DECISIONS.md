# LLM Design Decisions

This document explains why Letter Assistant is designed the way it is. Every decision here was made deliberately — not by default.

---

## 1. Structured Outputs with Strict JSON Schema

**Decision**: Use OpenAI's structured output feature with a strict JSON schema derived from the internal `LLMAnalysisResponse` Pydantic model.

**Why**: Free-form LLM text output is unpredictable. The internal schema validates only fields the model is responsible for generating, including `is_valid_letter` and its user-facing `message`. Backend-owned fields such as the original `letter_text` and rule-based confidence values are added afterward. The analysis service then converts the validated result into one of the public API models: `AnalyzeTextResponse` or `InvalidLetterResponse`.

This separation prevents the model schema from drifting away from the prompt while keeping the frontend response predictable and typed.

**Trade-off**: Maintaining separate internal and public models adds a small amount of schema code, but it makes ownership of every field explicit and prevents backend-generated values from being requested from the model.

---

## 2. Two-Layer Prompting Architecture

**Decision**: Separate letter analysis (Layer 1) from user interactions (Layer 2). Guided follow-up and reply drafting use selected fields from the validated Layer 1 output. Open chat uses both the original letter and that validated output so it can answer details that do not fit the flat analysis schema.

**Why**: Re-sending the full letter text for every guided question is expensive and unnecessary. Once the letter is analyzed and validated, focused follow-up prompts receive only the fields relevant to the selected question. Open chat deliberately retains the full letter because its questions are not known in advance.

**Trade-off**: Guided follow-up and reply drafting cannot recover facts omitted from Layer 1. Open chat can still refer to the original letter, but it remains restricted to that letter and cannot use external knowledge.

---

## 3. Grounding Over Retrieval

**Decision**: No RAG, no vector database, no external legal knowledge base.

**Why**: The system focuses on understanding a single uploaded letter. Grounding the model in the letter text and validated structured analysis provides a simpler and more reliable solution than introducing external retrieval.

**Trade-off**: The system cannot answer questions that require knowledge beyond the letter. When this happens, the model is instructed to say so clearly.

---

## 4. Rule-Based Confidence Level

**Decision**: `confidence_level` (high / medium / low) is calculated in `analysis_service.py` using explicit rules — not generated by GPT-4o.

**Why**: Asking an LLM to rate its own confidence produces unreliable and inconsistent results. Models tend to report high confidence even when output quality is low. A rule-based approach tied to measurable signals — text length, empty required fields, payment detection mismatch — produces a confidence label that is explainable and consistent across runs.

**Rules applied**:
- `low`: text under 200 characters, or `required_actions` empty, or both `sender` and `letter_topic` unknown
- `medium`: sender or topic missing; a payment letter lacks a recognizable IBAN or recipient; or urgency is not Low while `deadlines` is empty
- `high`: none of the above conditions apply

**Trade-off**: Rule-based confidence cannot capture subtle cases where the model understood the letter well but the text was ambiguous. It is a proxy for extraction quality, not a direct measure of LLM confidence.

---

## 5. Letter Verification Within Structured Analysis

**Decision**: The structured analysis prompt first classifies whether the input is an official German letter (`is_valid_letter: true / false`) and then either extracts fields or returns an invalid-letter result in the same model call.

**Why**: Irrelevant content such as receipts, casual messages, or random text should not produce a confident-looking letter analysis. The classification makes the system explicit about unsuitable input and prevents invalid content from entering follow-up, chat, and reply workflows.

**Implementation**: The verification is embedded in the same prompt as the full analysis. Because strict structured output requires one stable schema, an invalid result includes `is_valid_letter: false`, a non-empty localized `message`, and empty or neutral values for the remaining model-generated fields. After validation, the analysis service returns only the compact public `InvalidLetterResponse` containing `is_valid_letter` and `message`.

---

## 6. Explicit Output Language Parameter

**Decision**: Analysis, follow-up, and chat accept an explicit
`output_language`; `/translate` accepts a target language for an existing
analysis. Reply drafts are the exception and are always generated in German.

**Why**: The target users include international residents who may speak Turkish, Arabic, Persian, Hindi, or other languages. Rather than relying on auto-detection from chat messages — which is unreliable when the user writes in a different language than they want the output in — the system accepts an explicit language selection. This gives the frontend full control over which language the analysis, follow-up answers, and chat responses appear in.

**Implementation**: `output_language` is a typed `Literal` field defined in `schemas/common.py`, validated by Pydantic at the request boundary. 16 languages are supported. The prompt instructs the model to return all user-facing explanatory text in the specified language while keeping technical values (IBAN, amounts, reference numbers, dates, organization names, legal citations) unchanged. `confidence_reason` is localized separately via a backend dictionary — it is not generated by the LLM. The translation flow preserves the exact rule that produced the reason and translates that reason directly; it never maps every result at the same confidence level to one generic explanation.

Exact dates receive an additional deterministic grounding check. The backend
extracts and normalizes calendar dates from the source letter, supplies the
allowed dates to the analysis prompt, and rejects an analysis containing a
calendar date that is absent from the letter (apart from the injected current
date used for urgency calculation). This prevents a fluent summary from
silently changing a day, month, or year.

For Persian output, the translation prompt also requires context-appropriate
administrative terminology instead of literal dictionary substitutions. For
example, missing requested documents are described as incomplete or requested
documents, not as physically lost documents.

The `/translate` endpoint takes a full `AnalyzeTextResponse` and a target language, and returns a re-translated response. This enables instant language switching in the frontend without an additional LLM analysis call. Existing chat messages are not translated because doing so would add cost and could change meaning. The frontend instead keeps a separate in-memory chat history for each selected language and restores it when the user switches back.

**Trade-off**: Requiring an explicit language selection adds a UI element. Users who do not select a language default to English. Reply drafts are always generated in formal German regardless of `output_language`, since they are addressed to German-speaking institutions.

---

## 7. Reply Draft with Limited Intents

**Decision**: Reply drafts are anchored to one of three fixed user intents. Users may add short optional context, but it cannot replace the selected intent or override extracted letter facts.

**Why**: Fully open-ended reply generation is risky for official letters. Three explicit intents ("I already took care of it", "I need more time or have a question", "I disagree with this letter") keep generation bounded. A short context field adds practical details such as a requested extension date or a specific question without turning the feature into unrestricted drafting.

**Implementation**: The frontend sends one stable intent identifier
(`already_completed`, `need_more_time_or_question`, or `disagree`) and may send
trimmed `additional_context` of at most 1,000 characters to the dedicated
`/reply-draft` endpoint. Both the analysis and user context are treated as
untrusted prompt data. Conflicts are resolved in favor of the validated
analysis. The frontend owns the localized intent labels and presents the
complete German draft in an editable, copyable text area. Personal details the
system does not have are replaced with explicit placeholders.

---

## 8. Bounded Follow-up API and Frontend Quick Prompts

**Decision**: The backend exposes four bounded follow-up question types
(payment, documents, consequences, careful points). The current frontend uses
four quick prompts through open chat instead of presenting the bounded endpoint
as separate cards.

**Why**: Users often do not know what to ask. Quick prompts provide an easy
starting point in the product, while the bounded API remains useful for clients
that need predictable question categories and focused context.

**Trade-off**: The current frontend does not exercise `/follow-up` directly, so
that endpoint is verified by backend tests and API documentation rather than by
the primary browser workflow.

---

## 9. Streaming for Open Chat

**Decision**: The `/chat` endpoint uses streaming (`stream=True`) for regular chat responses.

**Why**: Letter analysis responses (Layer 1) are returned as complete structured JSON — streaming is inappropriate there. Chat responses are conversational and can be long. Streaming delivers tokens to the frontend as they are generated, which reduces perceived latency and makes the interaction feel responsive.

**Tone**: Chat uses clear, respectful, neutral language. It avoids slang,
emojis, jokes, overly familiar expressions, bureaucratic phrasing, and generic
customer-service filler. This is especially important for sensitive official
letters and for languages such as Persian where an overly casual translation
can reduce trust.

**Trade-off**: Streaming makes error handling more complex. If the model starts
a response and then produces an error mid-stream, the frontend has already
started rendering. The backend therefore emits typed SSE events (`token`,
`reply_options`, `done`, and `error`). It buffers only the short initial prefix
needed to detect `REPLY_DRAFT_REQUESTED`; ordinary chat content continues to
stream immediately after that check.

---

## 10. Safety and Privacy

**Safety note**: Every valid structured analysis response includes a required
disclaimer field. Its wording is localized and may vary, but it must explain
that the output is AI-generated help rather than legal advice and recommend
verification of important decisions.

This field is required by the Pydantic schema, and the prompt requires its
content to explain that the output is AI-generated help rather than legal
advice.

**Privacy**: Letter text and analysis are processed in application memory only.
No letter content is written to a database, log file, or persistent browser
storage. The frontend may retain up to three letters in active-tab memory until
refresh or tab close. Letter content is transmitted to OpenAI for model-backed
processing, so the system does not claim end-to-end local processing.

**Prompt grounding rules**: The prompts explicitly prohibit the model from inventing information not present in the letter. Rules include: use only the provided letter or structured analysis, do not assume missing information, do not provide legal advice, and do not guarantee outcomes. Letter text and structured analysis are treated as untrusted source data; embedded instructions that attempt to change the model's role, rules, or output format must be ignored.

---

## 11. Bounded Calls and No Synthetic Production Fallback

**Decision**: All OpenAI calls use configurable timeout and retry settings, and
analysis, follow-up, chat, and reply generation have explicit output-token
budgets. Missing or placeholder API credentials produce HTTP `503` instead of
sample content.

**Why**: Bounded calls reduce runaway latency and cost. Explicit failure is
also essential for trust: a generic or sample answer must never appear to be an
analysis of the user's real letter.
